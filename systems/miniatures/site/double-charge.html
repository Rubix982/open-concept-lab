The agent that charged twice

An AI agent buys things through a payment tool. It sends "charge $20" and waits, and no reply comes. Maybe the request was lost, maybe the reply was lost, maybe the server is just slow. The agent can't tell which, so it tries again, and sometimes the customer pays twice.

What to notice

No key: every retry that reaches the server is a brand-new charge. At the default settings 64 of 500 customers pay twice or more, $1,340 taken by mistake.

A key, checked then inserted: the agent sends the same key with every attempt, and the server looks it up before charging. That fixes the lost replies, but the server only writes the key down after the charge finishes. When it's slow, the retry arrives mid-charge, finds nothing written down, and charges again. 32 customers still pay twice. Set "server slow" to 0% and this drops to zero; set "messages lost" to 0% and it does no better than having no key at all.

A key, claimed atomically: the server writes "in progress" against the key before charging, in one step that can't be interleaved. A retry that arrives mid-charge waits for the first attempt and gets its result. Zero double charges, whatever you do to the sliders.

Retrying is what saves the purchases. With one try and no retries, 45 purchases never happen, and 58 more go through while the agent thinks they failed.

How the model works

Each message, request or reply, is lost 8% of the time and otherwise takes 50–150 ms. The server takes 0.1–0.3 s to make a charge, but 6% of the time it takes 1.2–3.5 s. The agent waits 1 s for a reply, then retries with the same key, up to 4 tries in all, and accepts a late reply to any of its attempts.

Every purchase has its own key, so purchases don't affect each other; each is played through with explicit timestamps for every message, which is what makes the race real rather than scripted.

An idempotency key is a unique ID the client attaches to a request, so the server can recognise a repeat. Stripe's API takes one in an Idempotency-Key header for exactly this reason.

The simulation is Go (sims/doublecharge), compiled to WebAssembly and run in your browser; go run ./cmd/mini double-charge prints the same comparison in a terminal. Its tests check the claims on this page, including that every check-then-insert double charge comes from overlapping attempts.
