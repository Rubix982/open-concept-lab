A hundred agents, one rate limit

A fleet of AI agents shares one API key, and the API allows only so many tokens a minute. Ask for more and it answers 429, "too many requests": try again later. What "later" means for each agent decides whether the fleet recovers smoothly from trouble or keeps making it worse.

How the model works

The API refills a bucket of tokens at the limit's rate (a token bucket) and holds at most one second's worth. A request that needs more than the bucket holds gets a 429; the agent hears about it 0.15 seconds later. An accepted request takes one to three seconds to answer, then the agent thinks for one to four seconds and sends its next one, between 500 and 4,000 tokens.

At the defaults the fleet asks for about 85% of what the key allows, so the limit is not the problem on average. The trouble is bunching: all hundred agents start within half a second, and from 50 s to 65 s the API is down and turns everything away.

Backoff doubles from 0.5 s up to a 32 s ceiling; "jitter" waits a random time between zero and that (the "full jitter" from the AWS Architecture Blog's Exponential Backoff and Jitter, 2015). The shared budget is a client-side token bucket at 97% of the limit that the agents queue at; after a failure it stops the whole fleet and sends one probe a second until one gets through.

The simulation is Go (sims/herd), compiled to WebAssembly and run in your browser; go run ./cmd/mini herd prints the same comparison in a terminal. Its tests check the claims on this page.
